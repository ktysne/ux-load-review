# UI の記憶、判断、操作を軽くする 8 規則

利用者が画面上の情報を思い出す、候補を比較して決める、操作対象を狙う場面で、記憶、判断、操作の負担を減らしているかを点検し、足りなければ補うためのスキルである。
このスキルが答える問いは、「利用者が、思い出さず、計算せず、狙わずに済むか」である。

## このスキルが守るもの

守るのは規則とその目的であり、特定の見た目ではない。
規則の説明に出てくる文言や画面構成は理解を助けるための例であり、アイコンの有無、配置、文言そのものを揃える必要はない。

適用の可否は、対象アプリの性質（利用者、利用頻度、作業の重要度、既存の UI 規約、技術的制約）を踏まえて判断する。
規則を機械的に当てはめると、候補の少ない画面に不要な検索や画像を足したり、見慣れた操作を利用者の経験に関係なく押し付けたりして、かえって負担を増やす。
各規則の「対象外」と「別の表現で満たす条件」を確認してから提案する。

## 進め方

1. **対象の把握**：どの画面、コンポーネント、フローを扱うかを特定する。
   アプリ全体の性質（業務システムか、一般消費者向けか、開発者向けか）と、利用者がその画面を使う頻度や前提知識を確認する。
   画面構成は、画面のルーティングとコンポーネントの一覧から把握する。
2. **負担の洗い出し**：対象ごとに、利用者が何を思い出し、何を比較し、何を計算し、どの対象を狙うかを列挙する。
   候補の発見、条件の確認、画面間の移動、候補の視覚的な区別、選択肢の比較、操作に必要な案内、言葉と動作の解釈、クリックやタップの狙いやすさを確認する。
   その画面に存在しない負担は対象外として記録する。
3. **規則ごとの判定**：該当する負担について、[references/rules.md](references/rules.md) のチェック観点で現状を確認する。
   判定は「満たす」「満たさない」「適用しない（理由）」「情報不足（確認事項）」の四つに分ける。
   「適用しない」にできるのは、その負担が発生しないか、発生しても利用者が困らない場合に限る。
   姉妹スキルの範囲に入る負担も判定に含めず、譲り先を理由に書いて「適用しない」とする。
   チェック観点どおりの表示や操作ができなくても別の手段で目的を達成できる場合は、rules.md の「別の表現で満たす条件」に従い、その手段の有無で「満たす」「満たさない」を決める。
   画面や実装だけでは分からない利用者の経験、実際の操作頻度、候補の選び方は、推測で判定せず「情報不足」として確認事項を添える。
4. **適用**：「満たさない」ものについて、そのアプリの UI 規約に沿った直し方を提案するか、依頼されていれば実装する。
   直し方は規則の目的と、実際に発生している負担から導く。
   規則の説明にある例をそのまま持ち込まず、対象アプリの利用者と作業に合う手段を選ぶ。
5. **報告**：後述の形式で結果をまとめる。

レビューだけを依頼された場合は 4 を提案にとどめる。
実装を依頼された場合も、規則の適用可否に判断が分かれる箇所は提案として残し、確実な箇所だけを実装する。

## 8 つの規則

各規則の詳細なチェック観点、対象外の条件、別の表現で満たす条件、実装上の注意は [references/rules.md](references/rules.md) にある。
判定するときは必ず参照する。

| 番号 | 規則 | 目的 | 対象となる場面 |
|---|---|---|---|
| 01 | 思い出させずに見て選ばせる | 利用者が候補を思い出して入力せず、画面上の候補から選べるようにする | 既知の対象を探して選ぶ場面 |
| 02 | 選んだ条件を確認画面に置いておく | 選択した条件を前の画面から思い出さず、確認画面で判断できるようにする | 注文、予約、申請などの最終確認 |
| 03 | ナビゲーションの並びと位置を安定させる | 画面が変わっても、同じ場所とラベルから移動先を予測できるようにする | 複数画面をまたぐ移動や共通ナビゲーション |
| 04 | 名前と内容に合う画像をセットにする | 視覚的な手掛かりで候補の内容を見分けられるようにする | 画像で候補を見分けられる一覧や選択 |
| 05 | 選択肢を整理して比較条件をそろえる | 候補を絞り、同じ条件で比較できるようにする | 候補が多い一覧や料金、機能の比較 |
| 06 | 必要な案内を操作する場所に置く | 操作に必要な情報を、その操作の場で確認できるようにする | 対象範囲、前提条件、選択の基準など、検証に関係しない案内が要る操作 |
| 07 | 利用者が慣れた言葉と動作に合わせる | 利用者が言葉と動作を学び直さず、予測どおりに操作できるようにする | 操作語彙やジェスチャーを選ぶ画面 |
| 08 | 操作対象を大きく近くに置いて押せる範囲を広げる | 操作対象を探して狙う時間と誤操作を減らす | クリックやタップの対象を操作する場面 |

## 適用判断の原則

規則を当てはめるかどうかは、次の順で考える。

- **その負担が実際に発生するか**：利用者が覚える必要のない情報を画面に追加しても、記憶の負担は減らない。
  利用者が既に確認できる情報を重ねて表示する場合は、追加表示が判断を助けるかを確認する。
- **利用者がその負担で困るか**：候補が少なく、違いが明らかで、操作も迷わず完了するなら、規則を追加して負担を減らす必要はない。
  困るが、チェック観点どおりの表示や操作ができない場合は「適用しない」ではなく、別の手段で目的を満たせるかを見る。
- **法則名だけで決めていないか**：心理学の法則は利用者の経験、作業頻度、情報量、画面の文脈で効果が変わる。
  法則名を根拠に一律適用せず、実際の画面でどの負担が発生し、提案した手段がどの機構で負担を減らすかを確認する。
- **既存の規約と衝突しないか**：アプリにデザインシステムや共通コンポーネントがあるなら、その語彙と操作で実現する。
  規則の目的を満たす別の表現が既にあるなら、それを「満たす」と判定してよい。
- **プライバシーとコストに見合うか**：履歴や候補の表示は便利でも、個人情報や機密情報を別の利用者に見せる可能性がある。
  バックエンドの変更や利用者調査が必要な提案は、画面だけで実現できる部分と追加開発が必要な部分を分けて書く。

「対象外」と「別の表現で満たす条件」は判定が異なる。
「対象外」は負担が発生しないか、発生しても利用者が困らない場合であり、「適用しない」と判定する。
「別の表現で満たす条件」はチェック観点どおりの手段を使えなくても目的を達成できる場合であり、その代替手段の有無で「満たす」「満たさない」を判定する。

読み込み中、空、失敗、権限不足、削除、完了、入力不備の状態設計は ux-state-review で扱う。
このスキルでは、状態がある画面でも記憶、判断、操作の負担だけを扱い、状態に対するメッセージや遷移を改善する提案は ux-state-review に譲る。
操作後の結果を操作した場所で知らせる設計も ux-state-review の規則 08 に譲る。
空状態に添える初回案内を後回しにでき、あとから戻れる設計は ux-state-review の規則 02 に譲る。
操作に必要な情報を任意の案内（閉じられるガイドやツアー）として出す場合は、規則 06 で扱う。
操作の判断に関係しない告知や機能紹介は、負担の設計ではないので判定対象にしない。
文字の読みやすさや画面のまとまりは、このスキルの判定対象にしない。

判断に迷ったときは、規則の目的（表の「目的」列）に立ち返る。
目的が満たされていれば手段は問わない。

## 報告の形式

レビュー結果は次の形式でまとめる。
対象が多い場合は画面ごとに繰り返す。

```markdown
## 対象
（画面やコンポーネントの名前と、アプリ全体の性質の要約）

## 判定
| 規則 | 判定 | 現状 | 提案 |
|---|---|---|---|
| 01 思い出させずに見て選ばせる | 満たさない | 既知の対象を毎回手入力する | 現在の入力に応じた候補を操作場所の近くに出す |
| 02 選んだ条件を確認画面に置いておく | 満たす | 決定前に条件と単位を確認できる | なし |
| 04 名前と内容に合う画像をセットにする | 適用しない | 候補を画像で区別する必要がない | なし |
| 07 利用者が慣れた言葉と動作に合わせる | 情報不足 | 想定利用者の経験と用語の実態が不明 | 利用者の作業語彙を確認してから再判定 |
| ... | | | |

## 優先して直す項目
（利用者への影響が大きい順に、理由を添えて）

## 判断を委ねる項目
（適用の可否や追加開発がアプリの方針に依存するもの。選択肢と推奨を添えて）
```

「判断を委ねる項目」には、規則の適用によって開発者が決めるべきこと（履歴を保存する期間、候補を絞る仕組み、画像を用意する範囲、操作対象を広げる実装など）を残す。
自走中はメインセッションの判断で推奨案を採り、決めるべき内容は一覧にして開発者に提示する。

## 実装時の注意

- 文言は、そのアプリの既存の文言のトーン（敬体か常体か、専門用語の使い方）に合わせる。
- 履歴や候補は利用者のデータとして扱い、表示範囲、保存期間、削除や無効化の手段を決める。
- 確認画面の条件は現在の選択値から生成し、戻って編集した値と表示がずれないようにする。
- ナビゲーションは位置だけに頼らず、ラベル、順序、現在地の表示を組み合わせる。
- 画像を使う場合は、名前や属性と対応する内容を選び、画像が伝える情報をテキストでも利用できるようにする。
- 選択肢を整理するときは、カテゴリ名と分類基準を利用者の作業に合わせる。
  料金や数量は同じ単位と期間で示し、判断に必要な説明を隠して候補だけを残さない。
- 案内は対象の入力欄や操作部品の近くに置き、入力前から見えるようにする。
  支援技術にも同じ情報が伝わるよう、入力欄との関連付けを実装する。
- 慣れた言葉や動作は開発者の経験で決めず、想定利用者の作業語彙、既存の道具、実際の操作を確認して選ぶ。
- タッチ対象は、プラットフォームや既存のアクセシビリティ基準にある目安（44 CSS px 前後など）を考慮する。
  固定値を到達目標にせず、対象同士の間隔、視認できるフォーカス、キーボードや音声での同等操作も確認する。
- 見た目より広い操作範囲を設ける場合は、隣接する対象と重ならないようにする。
  チェックボックスのラベル全体を操作範囲に含める場合も、別の選択肢を誤って選ばない間隔を残す。
- 変更後は、対象の各場面を実際の利用者の操作順で確認する。
  利用者の経験や操作頻度を再現できない場合は、確認できていない点として報告する。
